## 1. 核心判断

**现在最需要的不是继续堆内容或增加特效，而是让已有内容更可靠、更容易理解，并在手机上持续可用。**

项目已经从“可旋转的玩具地球”发展成了“地球—太阳系—深空—天象原理”的探索应用。视觉辨识度和功能规模已经具备，下一阶段应从“功能存在”转向“体验闭环”：

1. **先补可靠性与可操作性。** 图标按钮的无障碍名称、加载失败恢复、手机触控和键盘焦点，已经有可复现的问题。
2. **明确儿童产品的外部内容边界。** 直播电台不能仅凭名称关键词过滤就视为适合儿童；隐私概述应与真实联网行为一致。
3. **让“真实”和“示意”都说清楚。** 位置、大小、颜色、时间加速、历史状态和电台位置，不应给用户同一种精确性的暗示。
4. **建立跨场景的性能预算。** 地球已有 Worker、LOD、数量限制和自适应分辨率；但这些能力没有完整覆盖天象、预览、音频和资源生命周期。
5. **新增功能优先帮助理解。** 优先做引导探索、比较、保存视角和观测计划，而不是先做更多孤立的星体或更密集的光效。

建议产品定位：**适合亲子、教学和普通爱好者的可解释 3D 探索应用**。保持现有 Astrolabe 风格和程序化模型路线，不把它包装为测绘工具、实时天文观测服务或专业星历软件。

## 4. P0：先修复明确缺陷与发布门槛

### Q01：图标化之后，一部分按钮实际上“没有名字”

**状态：已复现。**

在银河系底栏读取无障碍树，12 个按钮全部只有 `button` 角色，没有名称。对应 DOM 中有 `data-tip`，但没有 `aria-label`，emoji 又设置了 `aria-hidden="true"`。

根因是 `tooltip.ts` 用 `textContent` 是否为空来判断是否需要自动添加名称；emoji 仍然计入 `textContent`，即使它对读屏是隐藏的。`title` 随后被移除，原来的名称来源也消失。地球时光机新增图标使用了同类结构，也应纳入修复范围。

**建议：**可交互图标的名称由创建按钮的代码显式提供，tooltip 只负责视觉提示。不要尝试用简单的 DOM 文本判空重新实现浏览器的 accessible-name 算法。中英文和状态变化时同步更新名称。

**验收：**太阳系、四个深空层级、时光机、天象和电台的图标按钮都有准确名称；无障碍树不出现无名称按钮；语言切换后名称更新；有状态的按钮正确暴露 `aria-pressed`/`aria-expanded`，不依赖颜色或 tooltip 才能理解。

### Q09：首屏与深链接启动路径仍有优化空间

**状态：本轮构建测量 + 代码确认。**

### Q11：本地优先不等于已经有可靠备份

### Q12：自动化测试要覆盖当前用户真正走的发布路径

**状态：代码确认。**当前不是“没有测试”，而是测试与功能增长、发布方式之间有缺口。

| 当前配置 | 缺口 |
|---|---|
| PR 跑类型检查和单元测试 | Pages 构建 job 排除 PR，PR 不能直接阻止所有构建/静态页面回归 |
| e2e 使用本地 Node 服务端 | 不等于验证了生产用的 `VITE_STATIC=1` + 子路径部署 |
| 浏览器项目为 Chromium 桌面与 Pixel 7 模拟 | 不覆盖 WebKit/Firefox 或真机 Safari |
| `openApp()` 默认 `?lowfx=1` | 大部分动态、高画质、真实性能问题不会进入常规用例 |
| `shot()` 保存截图 | 没有像素基线比较，保存图片不等于自动视觉回归通过 |
| 电台只开关面板，tooltip 只检查局部行为 | 不覆盖真实播放状态机、无名称按钮、键盘 focus 等 |

**建议：**PR 增加构建和一小组关键 UI smoke；完整 e2e 与多浏览器矩阵可分层/定时跑，不要求每次跑所有昂贵 3D 场景。为随机动画固定 seed/时间和相机，先对稳定的 UI 区域做视觉基线。

**验收：**能够自动阻止 Q01、Q02、Q05 的回归；静态子路径下地图、字体、懒加载、深链接、百科返回均有效；正常画质至少有覆盖地球、太阳系和天象的 smoke；测试结果保留可追溯的截图/trace。

证据：[CI 工作流](../../.github/workflows/pages.yml)、[浏览器与服务器配置](../../playwright.config.ts)、[e2e helper](../../tests/e2e/helpers.ts#L1-L26)。

### Q13：翻译与规划文档需要一个可信的当前版本

**状态：代码确认。**

当前支持语言是 `en / zh`，旧 PRD/backlog 仍包含韩语、日语目标，甚至把背景音乐和中文城市名列为待做。旧测试数量、资源体积也不再代表现状。继续按旧表排期会重复开发。

翻译方面，已完成的大部分中文不应重做，但仍有边缘文本：入口的 `Link expired`、照片的 `Globe photo` 等。电台标签映射是启发式分类，不应把“隐藏未知标签”视为完整翻译。

**建议：**将旧规划标为历史基线，以本文作为当前优先级入口；中英词典键和模板参数自动核对；关键操作名称采用受约束的 key 类型；动态状态、错误、aria-label、静态页分别覆盖。天体编号与刻意保留的英文别名无需机械翻译。

**验收：**当前语言/功能/部署说明没有相互矛盾；中英文关键流程无未声明的英文回退；资料编号保留；功能新增同时更新测试映射和文档，而不是维护过时的手写测试数量。

证据：[语言范围](../../src/shared/data/types.ts#L3-L5)、[错误文本](../../src/client/main.ts#L232)、[照片替代文字](../../src/client/ui/photo.ts#L58-L65)、[原 backlog](backlog.md)、[原 PRD](../product/prd.md)。

## 6. P2：渐进式架构治理，不做推倒重来

### Q14：提取共享规则，而不是先换框架或渲染引擎

当前 `styles.css` 约 1,325 行，`hud.css` 约 443 行；`globe/scene.ts`、`solar/view.ts`、`solar/deep.ts` 都超过千行。行数不是缺陷，但跨文件覆盖样式、场景状态分散会让之后的改动越来越难验证。

**推荐边界：**
- 统一按钮尺寸、字体层级、面板间距、状态颜色、z-index 和安全区 token；静态页面的生成样式也复用这些契约。
- 提取小型场景生命周期接口：进入、暂停、恢复、退出、可选销毁、当前位置序列化。暂不强制合并所有 renderer。
- 沿已有 `occluders.ts` 扩展遮挡注册，避免每个标签系统再维护一份硬编码选择器列表。
- 逐步分开渲染、相机输入、选择状态、标签布局与业务卡片；只在修改相关模块时提取，避免一次性重构所有场景。

**验收：**一次全局字号或按钮尺寸修改只需调整单一来源；同一个遮挡注册能覆盖新增面板；新场景不再复制全套全局工具栏。完成 Q01–Q13 不以本项大重构作为前置条件。

证据：[共享遮挡机制](../../src/client/ui/occluders.ts)、[全局/局部 UI 决策](../architecture/adr.md#adr-029-global-vs-local-chrome-ui-aware-labels-and-living-deep-space)。

## 7. 新功能：按用户价值而不是视觉新奇度排序

### F01：引导式探索与上下文推荐 — P1 / M

**为什么优先：**已有 536 个地球条目和多层宇宙，但现有七步教程主要介绍地球操作；进入深空后，用户仍可能不知道“能做什么、为什么值得看”。

**最小版本：**先做三条 3–5 分钟路线：“从家园到银河系”“为什么发生日食”“跟着一种动物迁徙”。每步复用已有相机、对象、卡片和天象视图，只增加目标、解释、继续和退出。

**不做：**强制教程、强制登录、复杂成就经济、无限推荐流。保留自由探索；最近访问和推荐逻辑先在本地运行。

**验收：**新用户能不靠开发者解释完成一条路线，说清其中一个现象，并知道如何回到自由探索。建议先做 5–8 组亲子/普通用户试用，记录行为和反馈，不把小样本比例当市场结论。依赖 Q02、Q06。

### 7.2 C01：内容扩充采用“主题包”，不再仅追求总数 — P2 / 持续

下面是候选方向，**不是在未做数据去重前认定这些主题完全没有内容**。每包先审查已有条目与模型，优先补深度和关联；建议单包新增或升级 5–10 项，完成来源、双语、模型检查和手机预算后再扩下一包。

| 分类 | 优先深化方向 | 真实性要求 |
|---|---|---|
| 地标 | 建筑结构、同类建筑比较、典型文化区 | 比例、关键轮廓、建造年代有依据，不只换颜色 |
| 动物 | 栖息地—食物—行为关联，海洋/鸟类代表 | 区分代表性位置与真实分布范围 |
| 发现 | 从发现现场到科学原理的小故事 | 明确发现者、证据和年代，避免把争议写成定论 |
| 交通工具 | 推进原理、运输路线、速度比较 | 路线是演示还是历史线路必须说明 |
| 恐龙 | 地质年代、体型、化石发现地 | 区分化石发现地与生活分布，不把所有恐龙放同一时期 |
| 美食 | 地理、原料、文化传播 | 对起源争议保持适当表述 |
| 节日 | 节日与历法、季节、地方习俗 | 区分固定公历日期与每年变化的农历/其他历法日期 |
| 航天 | 任务—发射地—目的地关系 | 历史事实与当前任务状态分开维护 |
| 植物 | 生态带、传播机制、典型结构 | 季节与地域条件明确，不把代表点当分布图 |
| 运动 | 运动中的物理、地理起源 | 对争议性起源使用多来源或保守措辞 |
| 火山 | 盾状/层状火山、板块环境 | 历史喷发与实时状态分开，不生成“实时预警” |
| 迁徙 | 一条完整季节路线，停歇点与原因 | 实际路径会波动，示意路线不能冒充追踪数据 |
| 航海 | 旅程阶段、导航与洋流 | 标明历史路线的近似程度 |
| 人物 | 人物—地点—发现—时代关联 | 关注贡献与背景，审查年代和归属的简化 |

深空内容则优先“解释性实验”，而不是再加一批难以区分的图标：

| 层级 | 优先候选 |
|---|---|
| 太阳系 | 大小/距离比较、季节与自转、任务目的地 |
| 银河系 | 恒星生命周期、星团与星云差异、太阳所在位置 |
| 本星系群 | 星系形态比较、卫星星系与潮汐作用 |
| 拉尼亚凯亚 | 星系团、超星系团和流场的区别，边界不是实体外壳 |
| 可观测宇宙 | 光行时、回望过去、红移与当前距离的区别 |
| 天象 | 将已有现象串成“预测—观察—解释”的小任务 |

新增对象的交付清单应包括：唯一 key、来源、名称与别名、中英简介、模型参考、位置/尺度的真实或示意标识、点击与搜索可达性、性能预算、与现有内容的至少一条关联。

### 7.3 P3：暂缓的方向

| 方向 | 暂缓原因 | 何时重新考虑 |
|---|---|---|
| 实时天气、卫星、新闻与大量实时天文源 | 引入可用性、时效、费用和来源维护负担 | F04 有真实用户需求，且有离线/断流降级方案 |
| VR / AR / 第一人称自由漫游 | 输入、相机、性能与内容制作成本同时增加 | 普通手机核心体验稳定后 |
| 全量 WebGPU、换前端框架、合并全部 renderer | 容易把质量修复变成长期重写 | 性能分析证明现有架构存在无法局部解决的瓶颈 |
| 聊天、排行榜、公开儿童资料、多用户实时世界 | 与当前匿名、亲子、低运营负担方向冲突 | 有明确监护、审核、数据治理和持续运营能力 |

| 大规模写实材质与超高面数模型 | 可能损害下载、手机帧率与风格一致性 | 少量重点模型对照试验确实提升辨识和学习效果 |

## 8. 建议采用的验收门槛

下面都是**后续目标，不是本轮已经达到的结果**。先确定代表设备、网络和场景，再锁定门槛；不能用桌面软件渲染器的结果替代真机验收。

| 维度 | 建议门槛与测量方式 |
|---|---|
| 首次可操作 | 选定中档 Android 和 iPhone，各自冷启动至少 5 次；固定约 10Mbps/100ms RTT 的网络条件，目标中位数 ≤6s；区分 UI 可操作、地球首帧、首个模型可点击 |
| 移动端流畅性 | 每个代表场景操作 60s；目标帧时间中位数 ≤33.3ms、P95 ≤50ms；最差场景达不到时应明确降级，而不是只报告全场景平均值 |
| 长时间使用 | 每台代表设备连续探索 15 分钟；记录温升后的帧时间、浏览器重载、音频状态，热降频失败须如实列出 |
| 内存与资源 | 固定路径进入/退出天象和详情 20 次；renderer 的纹理/几何数量回到预期缓存范围，不持续线性增长；JS heap 仅在支持的浏览器作辅助指标 |
| WebGL 故障 | 模拟 context loss、恢复失败；可重试或进入静态内容，不停留在无说明的黑屏 |
| 触控与布局 | 320/360/390/768px、横屏、200% 字号；主要触控目标约 44px；不能同时要求 320px 下 12 个 44px 按钮一行全部可见 |
| 无障碍 | 所有图标按钮有名称；重要状态可读；模态焦点正确；核心流程无需鼠标可完成；再安排 VoiceOver/TalkBack 人工检查 |
| 错误恢复 | 模块、地图、文章、电台、存储分别注入失败；每类都提供明确状态和可执行的恢复路径 |
| 科学表达 | 近似/示意可见，单位一致；高频事实有来源，时区处理有跨日/DST用例；不要用测试覆盖率百分比替代科学复核 |
| 内容闭环 | 每个新主题包至少一条引导路线、一项可回答的问题和一个自由探索出口 |
| 隐私与外部内容 | 关闭外部内容模式时不发起 Wikipedia/电台请求；导出/分享需用户主动触发；声明不作超出实际控制能力的保证 |

无需一开始就引入外部分析 SDK。性能面板和错误摘要可先本地化、按用户主动操作导出；如以后采集线上诊断，再单独定义最小数据、保留时间与用户控制。

## 11. 结论

最值得投入的下一阶段是：**让用户放心进入、准确理解、轻松操作、稳定保存，并在手机上连续探索。**

先把当前已复现的回归和发布边界补齐，再用“引导路线 + 比较 + 保存视角”把已有 3D 内容组织成真正的探索体验。内容扩充和画面升级继续做，但必须服务于辨识、解释和用户任务，而不是只增加总数、粒子或面数。
